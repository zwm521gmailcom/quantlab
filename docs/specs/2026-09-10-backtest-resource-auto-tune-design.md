# 回测运算资源自动配额

日期：2026-09-10

## 问题

QuantLab 会在内存不同的机器上跑同一套回测。当前：

- 全局闸门一次只跑 **一条** 回测（计划也串行）。
- 一条回测内部再开定长回看折线程、分层净值进程。
- 分层进程已按行情表大小和约 40% 内存预算降档；折并行仍主要按 CPU×0.8。
- 没有记下「这一条实际吃了多少内存」，换机器只能靠人改设置。

用户希望按设备自动判断并行度，并用历史消耗辅助配额。

## 决定

1. **同时回测条数保持 1。** 不根据历史消耗自动加第二条。一条回测的 spawn 进程已经装整表；再开一条等于再复制一份，16GB 上极易换页或被杀。
2. **自动配额只作用在一条回测内部：** 折并行、分层进程数。设置页/环境变量仍是「请求值」；内存预算是天花板，请求值不能突破。
3. **每条完成（或失败）的运行记下资源样本**，供下次同类回测当先验，而不是当爬升器。
4. **没有历史时** 继续用现有核数/表大小/内存启发式，行为与现在接近。

## 资源样本

写入 `backtest_runs.metrics_json.resources`，不进入收益/回撤等绩效字段：

| 字段 | 含义 |
|---|---|
| `peak_rss_bytes` | 回测进程树峰值常驻内存 |
| `elapsed_ms` | 墙钟时间（可与现有 `timing` 对照） |
| `frame_nbytes` | 主行情表 `memory_usage` |
| `fold_workers` | 实际使用的折线程数 |
| `bucket_workers` | 实际使用的分层工人数 |
| `bucket_pool` | `process` / `thread` |
| `cpu_count` / `ram_bytes` | 当时机器 |
| `signature` | 数据版本 + 训练/回测窗 + 模型 kind + 切折模式 |

采样：Unix `ps -o rss=`（KB）+ 子进程树，主线程里定时取 max。不新增 `psutil`。

查找先验：同一 `signature` 最近一条 `completed` 运行的 `resources`。SQLite `json_extract`，扫最近若干条即可，不改 schema。

## 配额公式

- **请求值：** 环境变量 > 设置页 > `max(1, round(cpu*0.8))`，再 `min(..., task_count)`（与现在一致）。
- **分层进程天花板：** 现有 `memory_safe_process_workers(frame_nbytes, requested, ram)`；若有先验峰值，用 `max(frame_nbytes, peak_rss_bytes / max(1, 当时 bucket_workers))` 作为单份成本再算一遍，取更小。
- **折线程天花板：** 仍受 CPU 限制。若先验 `peak_rss_bytes > ram * 0.45`，折并行降为 1（进程已经很肥，再叠训练线程容易顶满）。
- 环境变量/设置页的显式数字 **不能** 越过上述天花板。

## 展示

- 设置页 `compute_hint` 增加：本机内存、建议折/分层、**同时回测 1 条（固定）**、若有最近样本则显示峰值。
- 运行记录「模块耗时」旁展示本次 `resources`（峰值内存、实际折/分层）。旧运行没有该块时显示 —。

## 明确不做

- 计划内多条回测并行。
- 根据「没崩就 +1」自动提高同时回测条数。
- 跨机器共享配额文件、云端分析。
- Windows 专用采样（本机以 macOS/Linux 为准；采不到则不当先验，只走表大小启发式）。
